## 1.1 Approved decisions and implementation choices — 2026-11-14

Nin has approved implementation: reversible owner deactivation revokes every session; fresh verified-mailbox proof reactivates deactivated accounts without a session, never suspended accounts. Operator status routes stay in RBAC scope. Fresh dedicated email proof accepts irreversible deletion, atomically seals the account as pending deletion and revokes all sessions. Purge is resumable, targets 24 hours, and releases the email only after completion; re-registration always has a new UUID and no old data. Inactive deactivated/suspended owners can prove mailbox control for operation-scoped export/deletion, without ordinary login. Downloads expire after 24 hours and become unusable at deletion acceptance.

Approved retention defaults: minimized audit 180 days from event time; opaque deletion receipt 30 days from acceptance; backup/WAL 30 days; restoration ledger 90 days after completion; operational logs 14 days. The application enforces database/artifact/receipt/ledger retention. Infrastructure backup/log retention, restore-before-traffic deletion replay, Resend/provider retention and least-privilege maintenance credentials are deployment gates, not claims that local tests configure infrastructure.

Before shared-code edits, the following technical choices refine/supersede the draft details below:

- Only current product data is exported: the owner's account ID, current verified email/times, creation time and editable profile. Sessions, auth/audit/outbox/abuse records and future learning data are excluded. The small versioned JSON is generated by a durable job and stored encrypted in PostgreSQL using the existing AES-GCM keyring, with a distinct artifact associated-data UUID. No object-storage dependency or external files are added. Snapshot/publication uses one short transaction on the user row; future learning tables require a new inventory/snapshot design.
- OTP core gains operation binding, a lifecycle-revision snapshot, transactional after-start insertion, and operation-bound verification. Existing grants recheck lifecycle snapshots (including password sign-in after hashing). It alone purges challenge rows. Address advisory locks precede cooldown/proof locks for starts, signup verification and deletion acceptance/final purge. A short-lived HMAC deletion cutoff rejects unbound pre-deletion signup proofs. Actual issue/verification clock is checked after address waits. Pair start locks its address set in sorted order.
- Deactivation is bearer + explicit confirmation + expected lifecycle revision, with no replay receipt; a revoked-bearer retry is 401. Rights operations use a fresh 256-bit `vop_` capability generated at start, stored only as a hash, bound to action/operation and authenticated by a dedicated Rights wrapper. This is an explicit exception to the normal-session wrapper, never an inactive-bearer bypass. It authorizes only proof completion, limited operation status and its export download. Failed/inert starts remain indistinguishable. Receipt capability cannot authorize export or return account data.
- Durable database jobs run in the existing cleanup runner under an appended advisory job key, with bounded checkpoint transactions. Purge first removes bounded L2 challenges, then minimizes audit, then deletes remaining child/user data in ordered transactions; a failure leaves the account sealed and the job pending. PostgreSQL holds the artifact, so no unimplemented external-object cleanup step is claimed. Optional new lifecycle notification emails are deferred; proof email uses the existing encrypted outbox. Provider acceptance/late sends never grant access.
- A separate optional maintenance database URL/pool supports audit minimization/retention without granting the HTTP application arbitrary audit writes. Local disposable superuser setup can use the same URL; production must configure and verify restricted credentials. Admin endpoints, actual backup management, support recovery and future sync remain out of scope.

These decisions replace the five open approval questions for this implementation. Remaining sections describe baseline context and detailed behavior; any earlier proposal contradicted by this record is superseded. Actual contract and test evidence will be recorded at closeout.

## 3. Proposed state model, actors and access

### 3.1 States

State names below are product concepts; `deleted` is physical absence plus minimal operation evidence, not a retained user row containing personal data.

| State | Password / OTP sign-in | Refresh | Ordinary protected API | Sessions / data |
|---|---|---|---|---|
| `active` | Existing verified-account rules apply | Existing live-session rules apply | Existing bearer + owner checks | Normal data access; independent session controls remain available |
| `suspended` | Denied; public OTP/reset start stays generic and sends no login/reset code | `401`, never rotates into usable access | `401`; a role does not bypass own-account eligibility | Revoke **all** sessions at transition commit. Retain data pending a separate deletion decision |
| `deactivated` | Denied; ordinary sign-in does **not** reactivate | `401` | `401` | Revoke all sessions at commit. Retain account/email/data until reactivation or deletion; no automatic expiry proposed |
| `pending_deletion` | Denied, including ordinary recovery/reset | `401` | `401` | All sessions revoked; account is sealed for irreversible cleanup. Email remains reserved until final purge commit |
| `deleted` | No old account exists. Password/old OTP cannot recreate it. A fresh signup after email release may create a new ID | Old tokens are unknown and return `401` | Old tokens return `401` | User row and live owned data gone; only the approved limited receipt/security/restore records remain |

Restricted data-rights proof/receipt routes (§4–6) are not ordinary account access. Proposed export/deletion rights remain available by fresh mailbox proof to suspended or deactivated owners, without issuing a normal session or clearing a suspension. Pending deletion permits only its existing receipt read, not new exports, reactivation or cancellation.

### 3.2 Allowed transitions

| From → to | Requesting actor / proof | Result |
|---|---|---|
| No account → active | Existing verified signup | New UUID; never adopt a deleted user's identity/data |
| Active → deactivated | Owner with live bearer, explicit client confirmation | Reversible pause; revoke all, increment lifecycle revision, invalidate old proofs. A repeated or overlapping request revalidates the session and normally gets `401` after the first commit; that response alone is not a deactivation receipt |
| Deactivated → active | Owner using a **new dedicated mailbox OTP**, not password sign-in or an old token | Preserve ID/data. Return no session; require ordinary fresh sign-in afterwards |
| Active/deactivated → suspended | Future authorized operator, reason code and expected lifecycle revision | Store `resume_status` = active/deactivated; revoke all. Suspending a paused account must not lose its paused state |
| Suspended → saved resume_status | Future authorized operator with reinstatement capability | Increment revision; restore exactly the saved state, never a session. A restored deactivated owner still needs reactivation |
| Active/deactivated/suspended → pending_deletion | Owner with fresh dedicated deletion OTP + explicit irreversible confirmation | Seal account and enqueue durable cleanup. Suspension is not an automatic veto on an owner's data rights |
| Pending_deletion → deleted | System worker only after verified job acceptance and required purge steps | Remove user row, release email and mark receipt completed atomically |

No other transition is allowed: particularly no admin-created session, no suspended → active through a public code, no pending_deletion → active, and no deleted → previous account. A reversible deletion grace period is an alternative requiring a different cancel/recovery contract; **recommended default: no cancellation grace**. Cleanup latency is not a grace period. Client copy distinguishes reversible deactivation from irreversible deletion and offers export before confirmation.

**[Future RBAC dependency]** Existing role strings `user/admin/super_admin` are not sufficient authorization to ship operator lifecycle routes. Future permissions must define who can suspend/reinstate/revoke, permitted target roles, reason requirements, independent approval for exceptional rights actions, and last-Super-Admin protections. Proposed operator API: `POST /v1/admin/users/{user_id}/lifecycle-transitions` with `{action, reason_code, expected_revision}`; it stays **unregistered** until that design is approved and enforced. No admin export/download or forced deletion permission is implied here. Owner rights for an operator account must respect future last-owner safeguards without quietly destroying the last administrative account; resolve that integration before enabling such accounts in production.

**Amended 2026-11-15 by [TRD 06](06-rbac-user-administration-api.md) (approved by Nin): last-Super-Admin exception.** The operator routes now exist under TRD 06, including `POST /v1/admin/users/{user_id}/lifecycle-transitions` with `{action, reason_code, ticket_ref, expected_lifecycle_revision}`. Owner rights change for exactly one account, the **last active Super Admin**:
- `POST /v1/me/deactivate` returns `409 last_super_admin` and changes nothing.
- Deletion completion is refused with `409 last_super_admin` through `otp.Rollback`, so the proof is not consumed and is accepted once another active Super Admin exists.

Both transactions take the shared Super Admin guard (L2s: after L0 to L2b, before L3) and recheck the active Super Admin count under it. Every other owner, including a suspended or deactivated Super Admin (which no longer counts as active), keeps the rights above unchanged. A suspended owner who accepts deletion has the saved suspension cleared in the same update. Admins cannot suspend, reinstate or change the role of a `pending_deletion` account.

### 3.3 Boundary semantics

State + all-session revocation + lifecycle revision + audit commit together. Do not rely on the current best-effort per-request `account_inactive` revocation to sweep other sessions. Reinstate/reactivate increments the revision again and cannot un-revoke rows.

New authentication snapshots after the commit fail for every non-active state. As TRD 02 states, a read authenticated before the boundary can finish; already transmitted bytes cannot be recalled. Sensitive writes must revalidate user and acting session inside their transaction. Future sync writes must hold the same user boundary before accepting changes. A state transition never promises to roll back work that already committed.

## 4. Proposed proof and capability protocol

### 4.1 Fresh proof without a normal session

Use OTP core for distinct `account_export`, `account_delete` and `account_reactivate` purposes. Reuse 10-minute expiry, five wrong attempts, 60-second purpose/email cooldown and existing abuse controls; do not accept passwords, recent sign-in, TRD 03 proofs, login or reset codes as deletion proof. Each proof binds immutable action, operation ID, owner, current normalized email/email revision and new `lifecycle_revision`. Deletion also requires `confirm: "delete_account"`; reusing a code for another action/request/account fails. Missing old/current mailbox recovery remains deferred.

The signed-in UI pre-fills the verified address, but these flows also work after deactivation/suspension without treating an inactive bearer as valid. Public start normalizes email and always returns a real, same-shaped acknowledgement and an operation read capability; only eligible accounts receive mail. Unknown/deleted/ineligible accounts receive an inert challenge. Inert status never reveals whether the address exists. Completion must prove the code, capability and bound current identity in one transaction. No restricted proof ever grants learning-data writes, general account reads, refresh, reinstatement of suspension or arbitrary user selection.

### 4.2 Operation capability and retry recovery

**Proposal:** at start, return `{operation_id, operation_token, challenge_token, expires_at, resend_after}`. Generate a 256-bit opaque `vop_…` token before the transaction; persist only its hash. The client saves it in secure storage **before submitting the OTP**. This is a narrowly scoped capability to one action/operation, never an account session. A UUID, email, old bearer or request ID alone is insufficient.

Use `Authorization: Rights <operation_token>` on operation completion/status/download; never URL query parameters, email links, audit metadata or logs. A dedicated rights authenticator validates the token hash and derives the operation/owner/action from the row, not body IDs. Normal protected routes continue using `authenticated`. These non-session token routes need an explicit documented exception to AGENTS.md's Go route rule, analogous to the existing body-token refresh; do not weaken `authenticated` to admit inactive sessions. Add the new token prefix to logging/audit redaction and hygiene scans before enabling any route.

Before acceptance, a valid capability can see only `awaiting_proof`, `expired` or a generic failure, identically for eligible and inert starts. A deletion receipt becomes evidence of acceptance only after the destructive transaction commits. It reports `pending` until active-store cleanup finishes, then `completed`, with separate backup-expiry information. An expired/unknown capability is not evidence of success or failure. Proposed deletion capability/receipt retention: 30 days after acceptance; cleanup proceeds even if that capability expires. Export capability expiry is described in §5.

Completion retries authenticate the operation capability first. If that same operation was accepted, return its current result without consuming another OTP, writing another job or sending another notice. A mismatched capability gets generic `404 not_found`. A concurrent duplicate that waits on a consumed challenge re-reads its own operation result before reporting `invalid_code`; it must not claim failure for an already accepted operation. No router-wide idempotency cache or revoked-session replay exception is introduced. A lost start response has accepted nothing; start afresh under normal limits. A lost completion response is reconciled using the capability saved at start.

## 5. Proposed export flow and contents

1. Owner starts and verifies `account_export`. Eligible states: active, deactivated and suspended. The callback revalidates identity/lifecycle revision and creates one durable export job. Acceptance returns `202`; no provider or file generation occurs inside that transaction.
2. Worker reads from one PostgreSQL **REPEATABLE READ, read-only, owner-scoped snapshot** into a bounded encrypted scratch spool, closes the read transaction, then builds a versioned UTF-8 JSON archive (ZIP only when attachments require it) and uploads it. Enforce explicit row/byte/time budgets; exceedance fails/requeues visibly, never truncates a successful export. Delete scratch data on every terminal path; a future larger dataset needs an approved scalable snapshot strategy before those budgets are raised. Record `snapshot_at`, schema version and included/excluded categories. Future external blobs need immutable versions matching that manifest; fail rather than publish a silently incomplete archive.
3. Include account ID/current email and verification/creation times, editable profile, account state, safe session/device summaries, and all future owned learning content/relationships/history/sync metadata needed to interpret it. No passwords/PHC hashes, token/code hashes, pending credentials, OTPs, raw outbox payloads, capabilities, abuse keys, other people's data or privileged audit/operator notes. Raw audit rows are excluded; propose a separate owner-safe activity summary if approved. This product export is not claimed to answer every possible data-access request.
4. Encrypt temporary/artifact storage. Proposed default: private object storage with no public ACL; backend-authorized streaming download, no reusable public link. No artifact, token or attachment URL is sent by email. An optional ready notice says to return to the app.
5. Before publishing and on each download request, revalidate the operation, owner existence and captured lifecycle/email revisions. A valid capability may still read its own fixed terminal cancellation status until operation metadata expires; it exposes no current account data. A transition or email change invalidates an earlier export and cancels/deletes its artifact; a suspended/deactivated owner may prove again for a new export in that state. Deletion acceptance immediately prevents new downloads, even while object deletion is retrying. Bytes already downloaded cannot be withdrawn.
6. Proposed limits: one queued/running export per owner; one accepted export per 24 h; generation target 24 h; archive/download capability valid for 24 h after ready, then `410 export_expired` to an otherwise valid operation token. Delete partial files on failure/retry and ready files at expiry/cancellation. Keep only non-content operation status for seven days after terminal state, then remove it. Retry a failed accepted job internally without creating a second billable/export operation; a new request later produces a new snapshot.

Status projection: `{operation_id, action:"export", state, requested_at, snapshot_at?, ready_at?, expires_at?, schema_version?, size_bytes?, failure_code?}`. Never expose object-store keys or internal exception text. Download uses `application/json` or `application/zip`, safe fixed filename, `Content-Disposition: attachment`, `Cache-Control: no-store` and request ID. If deletion races an already-open stream, stop further reads when observed, but do not promise recall of sent bytes. No export is auto-created by deletion; user must download it before confirming deletion.

## 6. Proposed deletion flow, receipt and old devices

### 6.1 Acceptance and immediate access boundary

Fresh `account_delete` verification revalidates the bound user/email/lifecycle state, consumes its proof and accepts one deletion operation. In that transaction:

- Set `pending_deletion`, record acceptance time and increment lifecycle revision. Clear password hash and editable profile values; retain only the minimum user/email reservation required until final purge. No password or ordinary OTP can reactivate it.
- Revoke every unrevoked owned session including the caller; preserve pre-existing revocation history. Cancel export authorization and logically invalidate all earlier login/reset/set/email-change/rights proofs. Existing email-revision binding still applies independently.
- Persist the durable purge job/step state, minimal receipt and restoration-ledger entry, transactional success audit and optional fixed-copy acceptance notification. Mark the operation accepted only with this commit. Any audit/job/notification-enqueue failure rolls all of it back, including proof consumption.

Return `202` with the operation receipt projection, **not** `204 deleted`. Proposed projection: `{operation_id, action:"delete", state:"pending"|"completed", accepted_at, completed_at?, active_data_erased_at?, backup_expiry_due_at?, receipt_expires_at}`. Do not return email, user/profile data, internal cleanup errors or support/legal notes. `completed` means the active database, owned external objects and export copies have been purged and required audit minimization finished; backups remain subject to the separately stated deadline. Provider mail already sent is not recalled. `backup_expiry_due_at` is null while the last personal-data purge time is unknown; once complete it is `active_data_erased_at + 30 days`. Do not promise expiry 30 days after acceptance while failed cleanup could still create a later backup copy.

### 6.2 Bounded purge, email release and partial failure

Target active-store/object erasure within **24 h of acceptance**; no intentional reversible waiting period. Email stays unique/reserved while pending, including during outages. Retries continue from durable per-step checkpoints. Failed object deletion, a database batch or audit minimization leaves the receipt `pending`, preserves the deny boundary and never marks the account active again. Do not equate ordinary expiry cleanup or provider delivery with account erasure.

Purge owned challenges/requests, sessions/consumed hashes, outbox copies, future learning data, exported artifacts and applicable external objects in bounded batches. Erase separately retained deletion-notification recipients by their deadline. Finish privileged audit minimization and restoration evidence first. The last database transaction revalidates the deletion operation, confirms every required step, deletes the residual user row (FK cascade as a backstop), records completion and updates the receipt atomically. An external object must be durably confirmed absent before this final step; a timeout is ambiguous and must be retried/queried. An audit-completion failure rolls back the final user deletion and receipt update. Crash after deleting an already-checkpointed external object is harmless on replay.

The old address becomes available **only after that final user-delete commit**, not when deletion is requested. A new verified signup obtains a new UUID and default profile, with no old sessions, learning data, exports, receipts, role or entitlement restoration. While the old row is pending, signup remains generic/inert; it cannot steal the reservation. Retries/receipts continue to identify the deletion operation, never “whatever user currently has this email.”

**Stale public signup gap to close before implementation:** some signup challenges have no user FK and can predate an email being claimed by an account. Cascading the user is not enough to prevent such a challenge from creating a new account after release. Propose a short-lived, email-HMAC-keyed deletion fence with acceptance cutoff, retained through purge and for 24 h after email release. Signup proof issuance/verification and deletion acceptance/final release serialize on the address before taking OTP/user locks (§8). Verification refuses signup proofs issued before the cutoff; a fresh post-release start still works. This marker is abuse/retry evidence, not a permanent email ban. Test key rotation and expiry; deleting a marker cannot revive any still-usable old proof. The fenced signup start must capture its proof-issue database clock after taking the address barrier and derive expiry from that clock; an earlier transaction-start `now()` alone is insufficient after waiting. Fence comparison uses that immutable issue time. Keep all HMAC key versions needed to read unexpired fences across rotation. Enforce a proposed 60-second maximum mutation-transaction lifetime with database/connection cancellation safeguards; cleanup cannot remove a fence until every pre-cutoff proof and possible in-flight verifier is unusable.

### 6.3 Old devices and local data

Every old access/refresh token fails after acceptance, even if an offline device returns only after physical deletion or a new signup at the same email. No request may infer ownership from email or replace its stored user ID with a new one. A receipt capability can only read its own limited deletion status, not the new account.

Flutter follow-up: on a definitive inactive/unauthorized account response, clear secure auth tokens and stop cloud retries/uploads. Distinguish “unknown deletion result” from a generic `401`; use the saved receipt to resolve the former. The server cannot erase an offline notebook or a file already exported. Partition local caches, sync queues, cursors and sync writers by UUID. **Amended 2026-11-14 by [TRD 05](05-learning-data-sync.md) §9:** once deletion is confirmed (this device's accepted deletion response, or a receipt read with the saved capability), the client clears that account's local cache, queue, cursor, writer and restore-review set; it keeps no local copy. A deleted account's cache is never imported into any account, including a later account registered with the same email, and backups tagged with another `user_id` are refused. This replaces the earlier proposal to offer a local-copy choice and a consented import into a newly created account. Future sync must reject deleted/non-active owners server-side even when the device has stale local entitlement/session state. Remote device wipe is not promised.

## 7. Proposed erasure and retention policy

These are **approval candidates**, not assertions of deployed policy. Measure deadlines from database timestamps; temporary cleanup failure does not silently extend the promised target.

| Data/copy | Proposed treatment | Deadline / retained exception |
|---|---|---|
| User identity/profile/credentials | Clear password/profile at acceptance; delete residual row at final purge. Preserve data on suspension/deactivation | Active-store deletion target 24 h; email reserved until purge commit. Deactivated data otherwise retained indefinitely unless owner deletes — explicitly requires approval |
| Sessions/consumed refresh hashes | Revoke all at boundary; physically delete in purge, faster than normal 30-day retention | Within active-store target. Do not retain refresh hashes as deletion receipts |
| Owned OTP/email-change records | Logically invalidate at boundary, then core-owned purge/cascade including pending password/code material, address snapshots and request IPs | Within active-store target. Never sweep L2 rows after acquiring L3 |
| Unbound signup/inert OTPs | No user FK to cascade. Identify only current reserved-address records issued before the deletion boundary; never sweep a later signup or another owner's released-address history | Remove applicable rows using fenced/core-owned cleanup. Unattributable new inert rows retain ordinary expiry + 24 h cleanup threshold; document this limited operational retention rather than claiming all email traces disappeared |
| Outbox | Cancel/scrub pending owned messages, delete recipient/provider metadata and ciphertext in purge. Guard worker eligibility by lifecycle/operation state | Already reserved send can finish; a code cannot work. Optional deletion notice is an operation-linked, user-FK-free exception so purge cannot silently cascade it away; deadline 24 h, then erase recipient/payload even if unsent. No new state-based retry budget |
| Cooldowns/rate limits/address fence | Keep only existing pseudonymous/aggregate abuse controls; remove precise owner/session keys where safely attributable, never unrelated shared-IP records | Existing 24 h cooldown / 48 h counter retention; fence through purge + 24 h. Key rotation must not extend retention or let old proofs bypass a fence |
| Audit | Immediately minimize user-related IP, user agent, request ID, email HMAC and free metadata during purge; retain fixed action/outcome/reason/time and pseudonymous actor/target identifiers for a proposed **180 days from each event's occurred_at** | UUIDs remain linkable, so call this **pseudonymization, not anonymization**. Preserve authorized operator accountability; store only fixed non-content reasons. Then delete subject-related rows or irreversibly unlink identifiers under a documented policy |
| Deletion receipt | Capability hash, opaque operation ID, limited state/timestamps; no email/content/token plaintext or FK that disappears with user | Expire 30 days after acceptance. Unknown/expired receipt cannot prove deletion; internal cleanup continues regardless |
| Purge job / restoration ledger | Job may hold encrypted minimum recipient/address context only until needed steps finish; clear it at completion. Ledger keeps deleted UUID, operation ID, acceptance/completion markers, no email/content | Retain restore ledger 90 days after completion, beyond proposed backup lifetime; unfinished jobs do not expire while work remains |
| Export files/temporary blobs | Encrypt, authorize every read; delete on failure, transition, deletion or expiry | Ready file 24 h; terminal non-content export job metadata seven days. Cancellation immediately denies reads even if physical removal retries |
| Logs/metrics | No payloads/capabilities/credentials; avoid user-specific metric labels. Keep aggregate operational metrics; restrict any linkable logs | Proposed log retention 14 days; inventory deployments before enabling. Do not claim user-targeted erasure is possible for arbitrary historic unstructured logs |
| Backups/WAL/replicas | Delete live/replicated rows; encrypted immutable backups age out, not rewritten per user. Replay the restoration ledger before restored data becomes accessible | Proposed maximum recoverable backup/WAL lifetime **30 days**. Receipt reports backup-expiry due time; it does not claim immediate erasure of immutable copies |
| Provider/inboxes/operator copies | Inventory Resend retention, support exports, object-store versions/replicas and access logs; configure expiry/delete where supported | Exact provider/operator periods must be recorded before release. Delivered inbox copies and user-downloaded files are outside server recall; communicate that limit |

Audit minimization requires a narrowly privileged maintenance path and separate maintenance credentials/pool; the current API cleanup pool must not simply receive arbitrary UPDATE/DELETE on audit events. Attribute rows using actor/target IDs and bounded pre-acceptance email-HMAC evidence where possible; do not scrub a different new owner merely because the address was reused. HMAC-only records that cannot safely be attributed remain subject to the proposed 180-day audit limit (or the 24/48 h non-audit control limits), not an unbounded exception; record this residual linkable retention explicitly. Record a separate secret-free minimization completion event. Do not leave raw addresses or arbitrary support prose in metadata to evade the policy. If a future legal-hold exception is approved, it must identify purpose, authorized actor, data categories, expiry and user-facing effect; there is no blanket hidden hold or admin veto in this proposal.

Restoration procedure: restore in isolation, replay the authoritative ledger (including accepted/incomplete deletions), purge those UUIDs/owned copies, apply audit minimization, discard restored export artifacts and revoke restored sessions before traffic. Do not resume archived outbox sends, stale OTP grants or old export jobs. Validate backup expiry and run restore drills; backup expiry is an operational release requirement, not something PostgreSQL router tests alone prove.

## 8. Proposed API, persistence and transaction design

### 8.1 API surface

Paths and codes are proposals; implementation must update OpenAPI and real-router coverage together. JSON stays strict, bounded and rejects unknown/duplicate fields and query selectors. No user ID is accepted in self-service bodies.

| Operation | Authentication / request | Proposed result |
|---|---|---|
| `POST /v1/me/deactivate` | Normal live bearer; `{confirm:true, expected_revision}`. Expose read-only `lifecycle_revision` in GET me first | `204`; caller revoked too. Stale revision `409 lifecycle_conflict`; no receipt for this reversible action |
| `POST /v1/account-rights/{action}/start` | Public; action `export`, `delete` or `reactivate`; `{email}` | Generic `202` acknowledgement/capability (§4), including inert requests |
| `POST /v1/account-rights/{action}/{operation_id}/complete` | Rights capability; `{challenge_token, code}`; delete also requires `confirm:"delete_account"` | Export/delete: `202` current operation projection. Reactivate: `204`, no session; accepted duplicate same result |
| `GET /v1/account-rights/exports/{operation_id}` | Same export capability | `200` status; UUID alone reveals nothing |
| `GET /v1/account-rights/exports/{operation_id}/download` | Same export capability + snapshot/current-identity checks | `200` file, `409 export_not_ready` or `410 export_expired`; canceled generation `409 operation_canceled` |
| `GET /v1/account-rights/deletions/{operation_id}` | Same deletion capability | `200` limited receipt, including pre-proof `awaiting_proof`; unknown/foreign/mismatched/expired token all `404 not_found` |

Shared errors: malformed JSON/path/confirmation `400 invalid_request`; bad email at start `400 invalid_email`; proof wrong/expired/wrong-purpose/wrong-binding `400 invalid_code`, exhausted proof `400 code_attempts_exceeded`; unsupported content type `415`; limits `429` with Retry-After; unexpected storage failure `500 internal_error`. Normal invalid/inactive bearer remains `401 unauthorized` with WWW-Authenticate. Rights tokens authorize an operation; mismatch uses indistinguishable `404`, not an account eligibility explanation. If a correctly proven operation loses a state/revision race, return `409 lifecycle_conflict` with no partial acceptance and require a new proof. Accepted cleanup failures stay `pending`, with internal fixed failure classes; status does not fabricate a successful erase.

Reuse request ID, no-store, problem+json, constant error titles and existing limiter/audit conventions. Add action-specific start/verify and per-operation polling/download limits; proposed poll limit 30/minute/token and invalid-capability IP limit, alongside existing OTP limits. Avoid public enumeration through successful HTTP status, body shape, capability status or audit text. Timing still needs separate staging measurement; no new AC-7 proof is claimed here.

### 8.2 New persistence responsibilities and OTP changes

Propose forward migration(s), with exact version assigned at implementation:

- Users: nonnegative `lifecycle_revision`, state-change timestamp and constrained `resume_status` only while suspended. Store no `deleted` user row.
- OTP: three dedicated purposes, operation ID binding, lifecycle snapshot; carry these through `Target`/`Accepted`. General login/reset/set/email-change acceptance and password sign-in also compare lifecycle revision under L3, preventing active → inactive → active from reviving pre-transition work. Add signup-fence validation and worker eligibility reads.
- Rights operations: token hash, action, immutable eligible owner/email/lifecycle binding, awaiting/accepted/terminal state, timestamps and deadlines. Public inert operations disclose no owner and cannot be accepted. Separate minimal receipts from encrypted purge context so content can be erased without losing retry evidence.
- Export jobs/artifacts, durable purge jobs/step checkpoints, restoration ledger and temporary address fences. Receipt/ledger rows must survive user cascades; content-bearing owned jobs must cascade or be explicitly cleared. Define foreign keys/indexes and absence of retained personal snapshots in the final schema review.
- Revocation reasons/templates, pending-message lifecycle/operation binding, retention indexes and per-job advisory keys. Append cleanup job keys; never renumber current ones in a rolling deployment.

OTP core remains the **only** writer of challenges. Specify and test its new operation-binding, eligible inactive-state proof checks, revision validation and purge API before editing shared code. Do not implement deletion by copying OTP SQL into an account handler, and do not route inactive owners through normal login. Every older API instance that can issue a session/proof must enforce the new revision/fence rules before lifecycle operations are enabled. A public eligible OTP/rights start can read a user just before final deletion and then lose its user-FK insert race. OTP core must roll back that attempt and reconcile this specifically identified disappearance by rechecking eligibility and returning the ordinary inert `202`, not leaking it as a deletion-specific `500`. Unexpected FK failures remain errors. Caller-bound protected starts instead fail `401` when their account/session ceased to qualify. Test both paths without leaving cooldown, proof or outbox fragments.

### 8.3 Lock order and transactions

Preserve READ COMMITTED mutation transactions and whole-transaction `40P01`/`40001` retry helper. Rate-limit increments remain outside them; generate opaque secrets beforehand; count metrics only after commit. No object-storage, email-provider or archive-generation call runs inside a database transaction.

**Proposed narrow addition L0:** a transaction-scoped per-normalized-address advisory fence, with deterministic keys independent of email-HMAC rotation, acquired in sorted key order **before** L1/L2. Required for signup start/verify and deletion acceptance/final email release to enforce the stale-signup cutoff (§6.2). Derive the address from trusted snapshot lookup, then revalidate identity under L3. If source email changed, abort/restart rather than acquire another L0 lock after L3. Use a dedicated namespace, accept harmless hash-collision serialization, and never log the normalized address or lock-key derivation. This amends existing signup transaction structure and must be explicitly reviewed; it is not already implemented.

| Work | Lock/snapshot sequence |
|---|---|
| Rights proof start | Optional required L0 → L1 cooldown → L2 supersede own-purpose proof → eligibility read → L5 new proof/operation/outbox/start audit. Inactive eligibility is purpose-specific; no early user lock upgrade |
| Export/reactivate proof completion | L2 challenge → L2b owned operation → L3 user `FOR NO KEY UPDATE` → L5 job or reactivation state/audit; consume with callback atomically |
| Deletion completion | L0 current address → L2 deletion proof → L2b operation → L3 user `FOR NO KEY UPDATE` → L4b revoke all → L5 purge/ledger/receipt/audit/notification/cancel writes. Revalidate origin email, lifecycle and allowed state before destructive updates |
| Owner deactivation | L3 user → L4a revalidate acting session → L4b all-session revocation → L5 state audit/outbox. Commit state/revision with revocation |
| Future operator transition | Authorization outside target transaction; L3 target user → L4b all target sessions → L5 audit. Never hold the operator's session and then acquire a lower-level target lock; future RBAC must define transactionally safe actor authorization/revalidation |
| Owned purge batch | Claim durable job lease in a **separate** short transaction; then acquire candidate OTP L2 rows in UUID order before request L2b/user L3/session L4 locks as required. Recheck pending state/operation, erase only this owner's bounded batch, checkpoint and audit last. No job-row lock held while later taking L2 |
| Final physical user deletion | Required L0 → any remaining child L2/L2b locks first → users **FOR UPDATE from the outset** at L3 → remaining L4 rows → cascade/outbox/receipt/audit at L5. Do not upgrade `FOR NO KEY UPDATE` after holding children; pre-purge and verify children to keep this short |

Never sweep or delete arbitrary OTPs after locking users: a verifier may hold L2 while waiting for that user. Invalidation at the state boundary is a revision/state check, not an out-of-order physical sweep. Candidate rows are discovered without locks, acquired in order and rechecked; bounded cleanup must yield to legitimate in-flight work rather than changing order. Final cascade is a backstop after pre-purge: if a concurrent late old-revision insert leaves new children, roll back/retry through ordered child cleanup, not blindly cascade into an L2/user cycle. Apply transaction/lock-wait deadlines; correctness cannot depend on an unbounded transaction retaining old `now()` eligibility.

Refresh/logout retain their existing L4-only then L5 path and never request L3 afterwards. Audit has no user FK, avoiding an implicit reverse user lock there. A refresh that wins its session lock may return a pair; the transition waits, revokes the same row and that pair then fails. A refresh waiting behind revocation must return `401`. Sign-in/OTP issuance uses L3: if it wins, transition revokes its new session; if transition wins, eligibility/revision rejects the stale issuance. Reactivation/reinstatement permits only fresh later sign-in, not revival of old sessions/proofs.

Export snapshot creation intentionally uses REPEATABLE READ for a coherent read, separate from the short READ COMMITTED acceptance/publication transactions. A worker cannot infer current authorization from that older snapshot when publishing/downloading.

### 12.5 Restore-time reapplication of deletions

Before a restored database takes traffic:
1. Restore into an isolated instance with no API or worker attached.
2. Run `cmd/migrate up` to the current version.
3. Copy every `deletion_ledger` row from the live database newer than the backup, then, for each ledger `user_id` (completed or not), set the user to `pending_deletion`, revoke all sessions and make sure exactly one `pending` delete operation exists (reuse a restored accepted one; `account_operations_one_delete` allows only one), so the purge job erases it again under the normal checkpoints.
4. Discard restored export artifacts and `email_outbox` rows that were not yet sent.
5. Start the cleanup runner alone and wait for `account_deletion_oldest_pending_seconds` to return to 0.
6. Only then admit traffic.

[TRD 05](05-learning-data-sync.md) §8.2 adds the vocabulary steps: close `learning_sync_control` first, let the purge drain learning rows, rotate every sync epoch and retire every writer before reopening sync. The ledger is kept 90 days, longer than the 30-day backup window, so any restorable backup is covered. No restore tool exists yet: steps 3 and 4 are a manual SQL runbook to write and drill before release. Router tests do not prove any of this.
