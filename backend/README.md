# Veea backend (Go)

Go modular monolith on PostgreSQL, the only supported backend (TRD 01 R9). It includes TRD 01's email signup (OTP and password), OTP and password sign-in, sessions with
refresh rotation, first-password set, change and reset, the encrypted email outbox,
audit events, rate limits, the cleanup jobs, the metrics listener, TRD 02 session management and TRD 03 profile/email change. The schema is
migrations 00001 through 00015. Resend is selected for production email (TRD 01 R12) and by the current local Compose.
Local test harnesses explicitly select SMTP with Mailpit.

Staging readiness through migration **00015**: [`docs/staging-verification.md`](../docs/staging-verification.md).
Local evidence runner: `scripts/verify-staging-local.sh`; isolated logical restore drill: `scripts/test-restore-drill.sh`.
Independent deletion checkpoint commands: `bin/admin ledger archive`, `status`, `recover`;
see [`docs/deletion-ledger-recovery.md`](../docs/deletion-ledger-recovery.md) for dedicated
key/source custody, coverage requirements and private restore SQL. Recover/status need no
source database. Missing/behind checkpoints block reopening. The POSIX adapter is implemented;
an independent storage destination and its schedule/monitoring remain deployment prerequisites.
These do not deploy or open sync.

Design: [`docs/trd/01-email-authentication-account-foundation.md`](../docs/trd/01-email-authentication-account-foundation.md).

## Layout

```

cmd/api/                 HTTP service
cmd/migrate/             applies migrations, then exits (up | status)

internal/platform/

  db/                    pgx pool, transaction runner (READ COMMITTED, deadlock retry)

  db/sqlc/               GENERATED by sqlc, do not edit
  httpx/                 router, /healthz, /readyz, X-Request-Id
  logging/               redacting slog handler (passwords, codes, tokens never reach a log line)
  migrate/               goose runner (up-only, advisory-locked)
  pgtest/                disposable PostgreSQL harness for tests
internal/app/            wires every module into the router; used by cmd/api and the integration tests
internal/auth/httpapi/   auth HTTP handlers and the TRD 5.3 error mapping
internal/auth/session/   session issuance in the caller's transaction (tokens, cap), bearer authentication, refresh rotation, logout
internal/auth/signup/    Flows A and B: signup start (OTP, password) and verify
internal/auth/signin/    Flows C and D: OTP sign-in and password sign-in
internal/auth/password/  Flows E, F and G: first-password set, change and reset
internal/identity/accounts/  the only writer of users (database side of identity)
internal/maintenance/    TRD 6.10 cleanup jobs, run by cmd/api every 5 minutes under per-job advisory locks
internal/lifecycle/      TRD 04 deactivation, mailbox-proven export/deletion/reactivation, durable export and purge jobs
internal/learning/       TRD 05 vocabulary sync: writers, push/import, feed, snapshot, canonical encoder, purge and cleanup (ships closed)
internal/platform/metrics/  TRD 11.3 Prometheus metrics, served on VEEA_METRICS_ADDR
internal/auth/otp/       OTP challenge core: start (cooldown, supersede, challenge, email) and verify (procedure V, committed failures)
internal/audit/          append-only audit writer; refuses secret-looking metadata, redacts client text
internal/notify/         email outbox: encrypted enqueue (on the caller's tx), leased worker, templates, fake, SMTP and Resend senders
internal/ratelimit/      fixed-window limiter (autocommit, database time) and OTP cooldown (on the caller's tx)
internal/platform/clientip/  trusted-proxy client IP resolution, IPv6 /64 buckets
internal/identity/       email HMAC, email normalization, password policy and blocklist, Argon2id hasher (no database access)
migrations/              embedded goose SQL migrations (schema source for sqlc)
sqlc.yaml                sqlc configuration (pgx/v5)
test/integration/        tests behind the `integration` build tag

```

## Endpoints

- `GET /healthz`: liveness. Always `200` while the process runs; ignores the database.
- `GET /readyz`: readiness. `200`, or `503` (`application/problem+json`, code `not_ready`) when the database does not answer within `VEEA_READY_TIMEOUT`.
- `POST /v1/auth/signup/otp/start` `{email}` and `POST /v1/auth/signup/password/start` `{email, password}`:
  `202 {challenge_token, expires_at, resend_after}`, the same for new and existing emails. Only a
  new email gets a `signup_code` email.
- `POST /v1/auth/signup/verify` `{challenge_token, code, device: {name, platform}}`: `201` with the
  session tokens and the user, `409 signup_unavailable` if the email gained an account meanwhile.

- `POST /v1/auth/otp/start` `{email}`: `202`, the same for every email. Only an active, verified
  account gets a `login_code` email; sign-in never creates an account.
- `POST /v1/auth/otp/verify` `{challenge_token, code, device}`: `200` with session tokens.
- `POST /v1/auth/password/login` `{email, password, device}`: `200` with session tokens. Unknown
  email, wrong password and passwordless account all get `401 invalid_credentials`; a correct
  password on an inactive account gets `403 account_unavailable`. After 10 failures in 15 minutes
  password login is refused (`429`) while OTP sign-in keeps working.
- `POST /v1/auth/password/reset/start` `{email}`: `202`, the same for every email.
- `POST /v1/auth/password/reset/complete` `{challenge_token, code, new_password}`: `204`. Sets the
  password (also a first one on a passwordless account) and signs out every session.
- `POST /v1/me/password/set/start` (bearer): `202` and a code email, for a passwordless account;
  `409 password_already_set` otherwise.
- `POST /v1/me/password/set` (bearer) `{challenge_token, code, new_password}`: `204`. The code is
  bound to this session; the current session stays signed in and every other one is revoked.
- `PUT /v1/me/password` (bearer) `{current_password, new_password}`: `204`, keeps the current
  session and revokes the others. A resend after a lost response gets `403
  invalid_current_password`, and the confirmation email is the user's proof (TRD 01 §5.4).
- `POST /v1/auth/token/refresh` `{refresh_token}`: `200` with a new pair, rotated atomically
  with no grace window. A reused token (for example a retry after a lost response) revokes that
  session. Every refused token gets the same `401 unauthorized`.
- `POST /v1/auth/logout` (bearer): `204`, revokes the current session only.
- `GET /v1/me` (bearer): `200` with the account.

Protected routes need `Authorization: Bearer vat_...`; the session, its expiry and the account's
status and verified email are checked on every request.

Request bodies must be sent with `Content-Type: application/json` (with curl, add
`-H 'Content-Type: application/json'`; `-d` alone sends a form type, which gets
`415 unsupported_media_type`). A malformed body or a missing field is `400 invalid_request`.

The full contract is [`api/openapi.yaml`](api/openapi.yaml). Every integration test that goes
through the router validates each response against it, and a full run prints the documented
responses it never exercised.

Errors are `application/problem+json` with a stable `code` and `request_id` (TRD 01 §5.3). Bodies
are decoded strictly: unknown fields are `400 invalid_request`. A local run with
`VEEA_EMAIL_SENDER=smtp` and `make mailpit-up` shows the code emails at http://127.0.0.1:8025.

## Local Docker Compose

This is the default local backend. The root Makefile delegates `backend-*` here; there is one
Compose implementation. Needs Docker with Compose v2+ and `openssl`; no host Go SDK is needed.
Run the following from the repository root, or use `make -C backend <same-target>`.
The current `compose.yaml` selects `VEEA_EMAIL_SENDER=resend` and requires private
`VEEA_EMAIL_FROM` and `VEEA_RESEND_API_KEY` values. `backend-env` generates only database
and cryptographic keys; add the email settings before config/startup. Do not use
real delivery credentials in automated checks. For local-only SMTP integration use
`make -C backend test-flutter-go` or the disposable integration harness below.

```sh
make backend-env                 # Optional: backend-up also generates private keys once
make backend-config              # Validate without printing secrets
make backend-up                  # Always builds the image; migrates before starting the API
make backend-migrate-status      # current_version=15 pending=0
make backend-health              # /healthz and /readyz
make backend-ps
make backend-logs                # Follow; use BACKEND_LOG_ARGS='--no-color --tail=20' for a snapshot
make backend-down               # Keep database volume and .env
```

Default project: `veea-go`; default env: `backend/.env`. Override `COMPOSE_PROJECT_NAME` and
`COMPOSE_ENV_FILE` on **every** command for an isolated project. Relative env paths resolve
against `backend/` for both root and backend invocations; `--project-directory`, env, project
and Compose file are explicit. `backend-env` uses private atomic publication, independent
`openssl rand -hex 32` values (outbox prefixed with `1:`), and preserves an existing file.
Use [`.env.example`](.env.example) for port overrides and key formats. If you previously copied
the blank example, fill its keys yourself; setup deliberately never overwrites an existing file.

`backend-run` now aliases detached `backend-up`. `backend-down-v` explicitly deletes this
Go project's database volume; ordinary down preserves it. See the
[root commands](../README.md#local-go-backend). Removing the retired service does not
convert or delete its existing database volumes. Root `run-cloud` remains a Flutter launch, defaults to
the running Go stack's published URL, and requires startup first unless `API_BASE_URL` is
explicit. An explicit `APP_PORT` is a compatibility alias for `VEEA_GO_HTTP_PORT` when the latter
is not explicitly set. The backend health/URL targets discover the actual published port.

The image uses Go **1.26.2** from `go.mod`, checks that match during the build, and packages
`/app/bin/api`, `migrate` and `admin` as UID/GID **10001** with CA certificates and IANA zones.
The final image contains no Go toolchain. This stack is for local development: PostgreSQL 17
uses a project-scoped named volume with normal durability; Mailpit captures mail without relay.
The local database role also runs maintenance; production privilege separation is a separate
deployment configuration.

For direct Compose use, first run `make backend-env` from `backend/`, then the equivalent
commands below from that directory. Each generated key is independently random; no value is
a build argument, source file or image layer. Do not run with shell tracing. Make supplies
explicit paths/project automatically; preserve the same selection if invoking Compose yourself.

```sh
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 120
docker compose run --rm --no-deps migrate status
# Expected: current_version=15 pending=0
curl -fsS http://127.0.0.1:18386/healthz
curl -fsS http://127.0.0.1:18386/readyz
docker compose exec -T postgres psql -U veea -d veea \
  -c 'SELECT open FROM learning_sync_control;'
# Expected: f. Compose never opens the sync/install gate.
```

`migrate` waits for PostgreSQL's TCP healthcheck and exits after `up`. API startup requires
that exit to succeed, plus healthy PostgreSQL and Mailpit. These are Compose's
[`service_healthy` / `service_completed_successfully` conditions](https://docs.docker.com/compose/how-tos/startup-order/).
For an explicit operator command use, for example,
`docker compose run --rm --no-deps --entrypoint /app/bin/admin migrate` (prints usage).
Recovery-key custody and independent storage still follow the ledger runbook; neither is
provisioned by this local stack.

All host bindings are loopback: API **18386**, PostgreSQL **54328**, metrics **19090**,
Mailpit SMTP **1026**, inbox **8026**. Override `VEEA_GO_*_PORT` in `.env` if occupied.
The existing test scripts keep their separate 54329/1025/8025 ports and containers. The API
intentionally shares Mailpit's network namespace (`network_mode: service:mailpit`): its SMTP
address remains **127.0.0.1:1025**, preserving the sender's loopback-only security contract.
Consequently the API/metrics port mappings live on the Mailpit service. PostgreSQL remains
reachable as `postgres:5432` inside that namespace. The checked-in Compose currently
selects Resend, so Mailpit does not receive API mail. The SMTP address applies only
when SMTP is selected explicitly in a separate local configuration.

For a local-only SMTP smoke, use the disposable harness (from `backend/`):

```sh
make test-flutter-go  # Real Go router, disposable PostgreSQL and local Mailpit; synthetic fixtures
```

This harness supplies its own throwaway keys and SMTP configuration. It does not
use the Compose Resend settings or open the rollout gate.

The Compose Mailpit inbox is at `http://127.0.0.1:8026`; it receives no API mail while
Resend is selected. `docker compose down` followed
by `docker compose up -d --wait` preserves PostgreSQL data; keep `.env` and its keys too so
existing encrypted outbox data remains decryptable. Mailpit itself is ephemeral. `down -v`
deliberately removes this project's local database volume; use it only when discarding that
project's data. For isolated verification use a unique `-p <project>` on **every** command,
a private `--env-file`, and unused loopback ports. Never use `down -v` on another project.

## Production Docker (Resend, no Mailpit)

`compose.production.yaml` is independent of local Compose. It runs PostgreSQL 17 with a named
volume, a one-shot Go migrator, a transactional permission step, then the non-root Go API.
The API has its own network namespace and uses Resend over HTTPS; Mailpit is not included.
Default project is `veea-production`, env file `backend/.env.production`. These are separate
from local `veea-go` data and keys. No local users/data are automatically moved to production.

From the repo root, create a **new private** config (refuses overwriting an existing file):

```sh
(umask 077; set -C; cat backend/.env.production.example > backend/.env.production)
```

Fill it privately before running commands. Set `VEEA_PROD_IMAGE` to a versioned release tag
(for example `veea-backend:release-001`) when building locally, or a registry digest when
deploying a previously built/pulled image. Generate **each** DB password/HMAC/OTP key
independently with `openssl rand -hex 32`; outbox format is `1:<64 hex characters>`.
Set `VEEA_EMAIL_FROM` to a verified-domain bare address and inject the private Resend API key.
Never commit the env file or put values in shell history/logs. Keep application encryption/HMAC
keys and required old key versions with the durable database; do not regenerate on restart.

```sh
docker network inspect veea-camera_default >/dev/null # Existing Veea-camera network must exist
make backend-prod-config         # Validate without printing secrets
make backend-prod-build          # Build the configured tagged api/migrate/admin image
make backend-prod-up             # Use prebuilt image, wait for DB -> migrate -> grants -> API
make backend-prod-migrate-status # Expected: current_version=15 pending=0
make backend-prod-health
make backend-prod-ps
make backend-prod-logs            # Ctrl-C stops log following only
make backend-prod-down            # Preserve the production database volume
```

The same targets work with `make -C backend`. Use `PROD_PROJECT_NAME` / `PROD_ENV_FILE` on
every command to override the selection; relative env paths are backend-relative. Up never
builds or pulls implicitly. For registry releases, pull the configured image through your
deployment pipeline before up. There is deliberately **no production volume-wipe target**.

Fresh-volume initialization creates separate non-superuser migration, API and maintenance
roles. The migrator owns the database/schema; the API has no schema-creation permission and
can read/insert audit but cannot update/delete it. Maintenance can minimize/expire audit.
`permissions` reapplies table/sequence grants after migration and must succeed before API
startup. Bootstrap administrator credentials stay with PostgreSQL, not the API. Initialization
runs only on a **new** volume: editing password env values later does not rotate existing DB
roles. Perform planned SQL/secret rotation instead. This layout cannot adopt an arbitrary
existing database volume without a reviewed role/grant migration.

PostgreSQL publishes **no host port**. API defaults to `127.0.0.1:28386`, metrics to
`127.0.0.1:29090` for host checks and internal Prometheus. The API also joins the external
Docker network `veea-camera_default` with alias `veea-production-api` for shared ingress. The containerized Nginx in `Veea-camera` already
uses that project's default network and proxies to `http://veea-production-api:18386`.
PostgreSQL, the migrator and permissions job stay on this project's default network; only the
API joins both. The camera project owns `veea-camera_default`; backend Compose does not create
or remove it. On a fresh server, run `docker compose up --no-start --no-deps nginx` from
`Veea-camera` to create its network/container without starting Nginx before the backend is
available. Keep the camera project name `veea-camera`; changing it changes the default network
name. Preserve the existing backend project name, env file and database volume.

Start the backend and pass `backend-prod-health` before starting Nginx or reloading its updated
upstream configuration. No Nginx Compose network change is required. After later API container
replacements, validate and reload Nginx so its upstream address is refreshed. All other
upstream names in the shared Nginx config must also resolve on its attached networks.
See `Veea-camera/nginx/README.md` for proxy-side commands.

HTTPS termination remains an operator configuration: the existing Nginx stack exposes port
80 only. Before public traffic, configure TLS and block both `/v1/admin` and the public
`/v1/admin/` prefix; serve the admin console only on the approved operator ingress. Use
`VEEA_TRUSTED_PROXIES` only for the real trusted proxy path, accounting for any upstream TLS
proxy when forwarding scheme and client IP. Container-internal DB transport is confined to
the single-host Docker bridge; external database transport requires TLS design.

This is production orchestration, **not completed production acceptance**. Before traffic,
complete [the staging checklist](../docs/staging-verification.md): actual release image/commit,
verified Resend inbox delivery, native-device and AC-7 checks, ingress/alerts, and real backup/
restore with independent deletion-ledger custody. Named volumes are not backups. Configure
30-day backup/PITR, independent deletion checkpoints, restore drills, 14-day log retention and
monitoring outside this Compose file. API logs have size-based rotation here, not time retention.
The sync/install gate remains false on a new database and is never opened by these targets;
restarting an existing database preserves its current gate. Review any local edits to approved
rate limits and their TRD tests before creating a production release. No real production
deployment or email delivery is performed by the local verification.

## Schema and queries

Migrations follow TRD 01 section 6 and are listed in [`migrations/README.md`](migrations/README.md).
Queries live in `internal/platform/db/queries/`, grouped by domain (`identity`, `otp`,
`sessions`, `outbox`, `audit`, `ratelimit`, `platform`). Each query carries a comment with its
TRD reference and, for locking queries, its lock level from section 7.1. Locking queries are
named for what they lock (`LockUserForNoKeyUpdate`, `LockOTPChallengeByTokenHash`,
`LockActingSessionForUpdate`, `LockSessionByRefreshTokenHash`). Business rules such as
eligibility, caps and ordering of calls belong to the use cases, not to the SQL.

The generated Go code is checked in, so `go build` needs no tools. To change a query or a
migration:

```sh
make sqlc           # regenerate internal/platform/db/sqlc
make sqlc-verify    # compile queries, regenerate, fail if the output changes
```

sqlc is pinned in the `Makefile` (`go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1`), so every
machine produces identical output. It needs a C compiler, and network access the first time.
Run `make sqlc` and commit the generated files together with the query or migration change.

Query usage in a transaction (the caller opens it and passes it down, TRD 2.2):

```go
tx, _ := pool.Begin(ctx)
q := sqlc.New(tx)
user, err := q.LockUserForNoKeyUpdate(ctx, id) // L3
```

sqlc quirk: a typed interval literal such as `interval '1 second'` in the same statement as a named
parameter (`@name`) breaks sqlc's parameter rewriting with a confusing "syntax error at or near ..."
that points at a later token. Use `make_interval(...)` there. Literals in statements without
parameters, such as `now() - interval '7 days'`, are fine.

A query that matches no row returns `pgx.ErrNoRows`. Several queries rely on that on purpose
(for example `ClaimOTPCooldown` while a cooldown is active).

## Email

The API process runs the outbox worker (TRD 01 section 8.3) in the background. It reaps, claims
up to 20 rows, re-checks each linked OTP challenge, reserves a send (at most 5 per row), calls
the sender with a 30 s timeout and records the result only under its unexpired lease.

For local delivery start Mailpit and keep the default `VEEA_EMAIL_SENDER=smtp`:

```sh
make mailpit-up      # SMTP on 127.0.0.1:1025, inbox at http://127.0.0.1:8025
make mailpit-down
```

`VEEA_EMAIL_SENDER=fake` keeps emails in memory and delivers nothing.

For Resend, set `VEEA_EMAIL_SENDER=resend`, supply `VEEA_RESEND_API_KEY` through the deployment's
secret environment, and set `VEEA_EMAIL_FROM` to a bare address on a verified Resend sending
domain. Startup checks key/address syntax locally; it does not authenticate the key or verify
the domain over the network. Never put the key in logs, commands saved to shell history, or Git.

The adapter posts text and HTML to `https://api.resend.com/emails`, using the outbox row UUID
as `Idempotency-Key`. It performs no application retries or redirects; the existing worker
controls the send budget, timeout, leases and backoff. Resend retains keys for 24 hours; keep
From and rendered templates stable while rows are pending, since a changed request under the
same key is rejected permanently. Acceptance is not proof of inbox delivery. See TRD §8.3 and
§12.4 for outcome classes and the remaining staging checks. Local tests use `httptest` and
Mailpit, never Resend's live API.

## Integration tests

`VEEA_TEST_DATABASE_URL` must point at a throwaway PostgreSQL **on this machine**.
The harness refuses any host that is not `localhost`, a loopback IP or a unix
socket. Each test gets its own database cloned from a template that already has
the embedded migrations applied. The template's name includes a hash of the
migration files, so changing a migration builds a new one. Test databases are
dropped on cleanup. Old `veea_tpl_*` templates are harmless, and disappear with
the container when you run `make test-db-down`. Without the variable,

## Session management (TRD 02)

A valid bearer session can `GET /v1/me/sessions` to list its account's live sessions,
`DELETE /v1/me/sessions/{session_id}` to revoke another owned session, and
`DELETE /v1/me/sessions` to sign out all devices, including the caller. Client confirmation
is required before logout-all; no fresh password or OTP proof is required. The server
identifies the current session from the bearer principal, never a supplied device label.

Management writes share the issuance user-row lock and revalidate the acting session in
that transaction. A valid sign-in serialized after logout-all may issue a new session;
refresh cannot resurrect a revoked row. Retained already-revoked owned targets return 204
without another event; foreign and absent targets both return 404. Logout-all retries with
the revoked bearer return 401, which is not a receipt proving the earlier operation committed.
See [TRD 02](../docs/trd/02-session-management.md) for response fields, concurrency and audit evidence.

## Account profile and email change (TRD 03)

`GET /v1/me` and token responses include `User.profile`. `PUT /v1/me/profile` replaces display name, language (`en`/`vi`), IANA time zone and daily review target with an expected profile revision. Email cutover uses `POST /v1/me/email-change/start` and `POST /v1/me/email-change/{change_id}/complete`; both current/new OTP proofs bind to the request, account and originating live session.

Completion preserves the user ID and data, consumes both proofs, invalidates older bound challenges using `email_revision`, revokes every session, and enqueues both notifications in one transaction. Retry with the revoked bearer returns 401; recover a lost response through the confirmation email or sign in with the new address. Old-mailbox recovery and receipt endpoints are deferred. The old notification omits the new address.

Migrate before deploying. Every API instance must enforce challenge/password-sign-in email revisions before email cutover is enabled; an older instance could otherwise honor stale work. See [TRD 03](../docs/trd/03-account-profile-email-change.md) for contracts, lock ordering and verification evidence.
